# Fireflux 开发笔记

这里放的是**改代码前该知道的东西**：性能与节能设计的来龙去脉、看板娘的实现约束、内嵌网页（Memos）的诊断做法、
界面层踩过的坑，以及开发辅助工具的用法。
功能与安装说明见仓库根目录的 [README](../README.md)，客户端自身可调的参数见 [参数说明](参数说明.md)。

这些结论大多来自实测（`node scripts/bench-drag.mjs`），改动性能或看板娘相关代码前请先读一遍并复测。

## 性能与节能设计（硬件/软件渲染）

- **看板娘「静止肖像」策略（这是 CPU 占用的关键）**：软件渲染下看板娘每帧都由 SwiftShader 在 CPU 上完成，因此软件模式默认关闭内容区的全窗口跟随，只在看板娘区域、互动和动作尾随期间排帧；帧率上限 **60 帧**、画布分辨率默认 **0.8x**，静止时保留最后一帧并完全停止调度。用户可以在设置里重新开启全窗口跟随。硬件模式使用显示节拍，不设置人工帧率上限，并按设备像素比提高分辨率。失焦、拖拽和窗口缩放仍会暂停。
- **测量原则**：旧版基准中的 CPU 数字来自特定机器与旧的全局跟随策略，不能直接代表当前版本。性能归因台应分别测量硬件/软件、全局跟随开关、看板娘开关和拖拽场景；不要把历史数字当作新版本保证。
- **软件模式原则（改这块代码前务必知道）**：软件渲染下**任何持续动画**（哪怕只是两个装饰小光点）都会强制整窗重新合成，实测单独就能吃掉约一整核 CPU —— 侧栏流萤光点因此已删除，新增动效前请先算清代价；
- **节拍器按渲染后端选择调度方式**：软件和硬件模式都跟随 `requestAnimationFrame`；软件模式在显示节拍上限 60 帧，并关闭 Pixi InteractionManager 的独立 system ticker；两者在静止、失焦或拖拽时同样停止（见 `src/renderer/public/live2d/load/frame-pacer.js`）。
- **看板娘自建节拍器必须按毫秒喂 `model.update(dt, now)`**（2026-09 修）：库自己的路径是 `update(ticker.shared.deltaMS)`，内部 `elapsedTime` 也是 `performance.now()` 起的毫秒。早先按「秒」传（dt≈0.066）会让**所有依赖 dt 的平滑慢 1000 倍** —— 症状正是「鼠标挪动时流萤不看人、表情全都点不出来」；动作（motion）是相对时间比较，所以当时看着还能播，把问题掩盖了。
- **不要 stop 掉 PIXI 共享 Ticker，要按自己的节拍手动 `Ticker.shared.update(now)`**：PIXI 5 的交互系统把指针事件队列挂在共享 Ticker 上处理，库的「看向鼠标」「pointertap 命中派发」都走这条路。直接 stop 等于把追踪与命中全关掉（症状：部分动作、全部表情失效）。手动 update 不重启它的 rAF 循环，功能与省电可以兼得。
- **模型尺寸与位置对齐原项目**：`src/renderer/public/live2d/` 里的 `model/`（moc3/纹理/动作/表情/物理/音频）、`load/` 中的上游脚本、`firefly.css`、`assets/` 与上游项目 **Firefly Live2D Web & Userscript v6.6.2 逐字节一致**；新增的 `load/frame-pacer.js` 是管理器专用调度器（改动前用 `diff -r` 核对过）。差异只在两处：加载器是本仓库的省电分支，以及 `embed.html` 的画布配置 —— 现按原项目官方值设置 **scale 0.94 / offsetX -20 / offsetY 12**（触摸端 0.90 / -12 / 8），画布宽高取侧栏看板娘格子的实际大小（原项目文档即要求「根据页面布局设置桌面端和触摸端尺寸」）。管理器在此基础上再用 URL 的 `s/x/y` 叠加「调整看板娘」/设置页滑块，可用「↺ 恢复初始值」回到原项目初始状态。
- **交互菜单（🔙😊🔗❌）在容器里、桌子右边；容器 = 模型 + 菜单**（2026-09 改，用户要求「模型放大容器也放大、模型缩小容器也缩小，模型 + 右侧菜单 = 容器」）：容器右缘留一条 `controlsGutter`（40px）宽的带子专放这列按钮，模型只占左边 `容器宽 − 40`，按钮贴容器右缘、底边和桌子齐平（右边距 4px、底边距容器底 4px，与上一版「贴右上角一行」和「容器外浮层」都不同）。加载器开的 `embed: true` 管三件事：① **画面尺寸跟随容器实时变化** —— 这条是必须的：原来画面尺寸定死在 `embed.html` 加载那一刻，用户把「模型大小」调小、容器跟着缩小时，模型仍按旧尺寸绘制，表现就是被裁掉一角；② 按钮按容器高度等比缩放（容器随模型一起变矮，固定 34px 的竖排会超出容器被裁）；③ 🔗 的 `window.open` 交给父窗口（`ff-open-url` → 主进程 `open:external`）—— Electron 里它只会弹一个没有地址栏的裸窗口，用系统浏览器更正常。🔙「返回首页」在管理器里没有对应页面（原按钮的 `cfg.homeUrl` 会把 iframe 导航到软件自己），所以没有转发、按钮点了不会跳走。尺寸关系（`App.svelte` 里就是这几行）：容器宽 =「模型大小」(30%~100%) × (侧栏宽 − 26)，模型列宽 = 容器宽 − 40，容器高 = 模型列宽 ÷ 模型宽高比 + 2（+2 是取整余量：宁可容器比模型高两像素，也不要把模型顶边裁掉）。实测模型内容宽高比约 **1.51**；以侧栏拉到最宽 460px 为例，模型 100% / 60% / 35% 对应容器约 434×263 / 260×148 / 152×76，模型内容宽 394 / 220 / 112（都等于容器宽 − 40）。按钮列按容器高度等比缩放（12~34px），实测 148 / 140 / 72 高，任何尺寸都在容器内 —— 不裁切。容器上方那一摞也画在父页面（iframe 里的内容出不了容器，而容器上沿就是模型头顶，画在里面只能压在头发上）：**自下而上**依次是「看板娘的消息框」→「调整模式提示条」，都居中于模型那一列、宽度以那一列为上限、一行放不下自动换行。消息框文字由加载器用 `ff-say` 驱动（显示/收起时机沿用加载器原来的计时，嵌入模式下本地那个 `.ff-live2d-dialog` 不显示）；调整模式提示条字号固定 12px 不跟着模型缩放，没有消息框时它就直接贴在容器上沿之上（也就是流萤头顶上方）6px，有消息框时叠在消息框上面。两者都 `pointer-events: none`，不挡点击。
- **光标跟随（可选）**：看板娘区域内的指针由 iframe 自己处理；全窗口跟随由设置页开关控制。硬件模式默认开启，软件模式默认关闭，以免普通内容区的 `mousemove` 把 SwiftShader 渲染持续唤醒。父窗口合并高频指针事件后按当前后端的帧率转发，停止移动后回到静止肖像。
- **跟随灵敏度用库自带那套，加载器不做加速**（2026-09 定稿，用户要求「不要那么灵敏，保持原项目原有的灵敏度」）。中间试过一版自建「快速跟随」（指数逼近 + 线性追赶，实测 62~153ms 到位），比原项目明显更急、观感发飘，已回退：`FireflyLive2D.focus()` 直接转交 `model.focus(x, y)`，缓动仍由库的 `FocusController` 完成。
  实测（`FF_INTERACT_TEST=1` 的「视线收敛曲线」一段，跨半屏跳一次后每 150ms 采样）：**约 0.3~0.4 秒平滑到位**、小幅移动 0.1 秒内跟上；另用 Node 逐帧复刻库的 `update()` 模拟过 60fps 与不同显示刷新率两种情况（距离 1.0 时 300ms / 267ms，距离 2.0 时 500ms / 467ms）—— 说明这套弹簧基本与帧率无关，因此视线缓动主要由模型物理参数决定，而不是由固定低帧率决定。
  **踩过的坑**：`gazeRespMs` 这个读数原来只在「静止肖像」判定里采样，于是把管理器那 1.5 秒的「指针停下」宽限期也算进去了，读出 1.6 秒的假数据；改成每个渲染帧采样后才是真实的 0.3~0.4 秒。诊断读数在 `ff-diag?` → `gazeRespMs`。
- **后端自适应帧率（2026-09-21）**：硬件 WebGL 使用显示节拍且不设人工帧率上限；CPU 软件 WebGL 限制在 60 帧并降低分辨率。帧调度器返回 `false` 时立即停止并保留最后一帧，避免静态页面仍有定时器或 rAF 空转。
- **停止移动不再把视线收回正前方**：早先为了让静止肖像「看起来不歪」，定格前会把视线归零 —— 但光标明明停在窗口里，收回正前方反而像突然走神。现在定格保留最后一次的视线方向，并多加一个条件：视线没贴住目标时再多渲染一帧，避免定格在「头转到一半」。
- **拖拽手柄居中**：侧栏那条拖拽条右侧是「2px 外边距 + 内容区 14px 内边距」、左侧只有 2px，手柄看上去偏左不居中；`DragBar` 新增 `gapLeft` 参数把这段差值补到左边（App 传 14），实测手柄 x 与两侧可见面板的中点完全重合（左 387/387，右 908/908）。
- **分隔条只有实时预览一种**（2026-09 起：设置页里的「拖拽方式」「拖拽轻绘模式」两个开关已按要求删除，`ff.drag-mode` / `ff.drag-lite` 两个键随之废弃）：拖动中布局实时跟随鼠标、文字实时重排、**壁纸照常显示**；指示只用那一小段短手柄（就在两块面板中间），**没有贯穿整窗的长线**。实测真实拖拽约 **4.4 核**（优化前约 7~9 核）。轻绘模式的省电数据保留在这里备查：开轻绘时约 2.5 核，只移动分隔条约 0.3~1 核
- **两条分隔条互不干扰**（2026-09 修）：内容页是「列表 | 编辑器」，中间那条分隔条现在调的是**编辑器宽度**（`ff.editor-w`，默认 560），列表改成 `flex: 1` 吃掉剩余宽度。拖侧栏那条时「列表左边界动、编辑器宽度不变」，于是中间分界线（右对齐、定宽）纹丝不动；拖中间那条时列表左边不动 —— 与「拖右边那条不影响左边」完全对称。实测（`node scripts/bench-drag.mjs` 输出按下前/拖动中/松手前三份几何）：拖侧栏时分界线三次采样都是 x=783、编辑器恒为 560px，列表 308→468→309；拖中间条时侧栏条恒为 x=434
  **顺手踩的坑**：定宽面板从列表换成编辑器时，`DragBar` 的 `side` 必须同步从 `right` 改成 `left` —— 否则方向会反过来（编辑器右对齐，鼠标往右拖反而把它拖宽、分界线往左跑）。判据是 `DragBar` 的语义：「手柄在面板哪一侧就往哪一侧拖变宽」，改完拖中间条时编辑器 560→626、分界线 x 从 783 跟到 679
- **背景预烘焙（拖拽/悬停 CPU 的关键优化）**：软件渲染下**每次布局变化都要重画整个窗口**，而旧版背景是「整窗线性渐变 + 4K 壁纸 cover 缩放 + opacity 混合」三层叠加，每帧重画约 0.05~0.10 CPU 秒 —— 这才是「拖一下 CPU 就飙升」的真凶。现在启动（及窗口尺寸变化）时用 canvas 把「渐变 + 壁纸（含暗度）」预合成为一张**设备像素 1:1 的不透明 WebP 位图**（`src/renderer/src/lib/bg-bake.ts`），每帧只剩一次 1:1 blit，视觉完全一致
- **指示器设计教训**：旧版「只显示分隔线」模式画了一条 2px 贯穿整窗的线，位置按「拖拽条中心 + 位移」算，而卡片边缘在拖拽条左侧约 20px —— 用户看到的就是「线在右边、光标在左边，拖完落点对不上」。现在只保留那一小段短手柄，**不吸附、不跳位**，布局跟手、拖拽条被布局带着走，手柄始终在两块面板正中。另外细元素位移**必须用 transform**，用 `left` 定位会让 fixed 元素触发整窗重绘（实测真实拖拽 2 核 CPU）
- **硬件加速渲染（实验）**：设置页可开启，允许 GPU 独立进程参与渲染（对显卡驱动被远程工具/虚拟显示驱动干扰的机器可能无效，需环境配合）；驱动崩溃时自动回落软件渲染

## 内嵌网页（Memos）：把「加载失败」变成看得见的东西

**问题**：动态页用 `<webview>` 内嵌远端 Memos。里面的图片裂开、连接被拒、证书不受信任，**渲染层一个事件都收不到**——
Chromium 只把 `net::ERR_*` 写到 stderr（例如 `ssl_client_socket_impl.cc:896 handshake failed ... net_error -100`），
既没有 URL 也不进界面，用户看到的只是一片白或一张裂图，连「是哪个请求挂了」都问不出来。

**做法**（`src/main/services/webdiag.ts` + `webview:diagnostics` 通道 + 动态页面板）：

| 钩子 | 拿到什么 | 用途 |
|---|---|---|
| `session.defaultSession.webRequest.onErrorOccurred` | 每个失败请求的 URL 与 `net::ERR_*` | 图片裂开只有这条路能看到（`did-fail-load` 不报子资源） |
| `app.on('certificate-error')` | 出错的 URL、错误码、证书签发者 | 自签证书一眼可辨；弹窗询问是否放行 |
| `app.on('web-contents-created')` → `setWindowOpenHandler` | webview 里的 `window.open` | 交给系统浏览器，别弹裸窗口 |

界面侧只做三件事：`did-start-loading`/`did-finish-load` 显示状态、`did-fail-load` 给出主文档失败横幅、展开面板列出最近的失败（每 2 秒拉一次）。

**踩过的坑（改这块必看）**：

1. **必须过滤 `net::ERR_ABORTED`**：页面跳转、被替换、用户取消的请求都会以此上报，不过滤的话面板全是噪声。
2. **`certificate-error` 的处理函数是同步的**：必须同步调 `callback(true/false)`，否则请求一直挂着；要放行得先 `event.preventDefault()`。
   弹窗用 `dialog.showMessageBoxSync`，并且**每个主机只问一次**（`askedHosts`），否则一个页面几十张图就是几十个弹窗。
3. **证书错误对子资源同样触发**：所以「图片裂开但没弹窗」基本可以排除证书问题。
4. **`did-fail-load` 只报导航（主框架/子框架）**，子资源失败不触发 —— 图片的问题只能在主进程侧记录。
5. **`allowpopups` 不配 `setWindowOpenHandler`**：Memos 里任何 `window.open` 都会开出没有地址栏的裸 Electron 窗口；
   现在统一走 `shell.openExternal`（只放行 http(s)）。
6. **验证方法**：不需要真的把服务器弄坏，在动态页按 F12 执行一次注定失败的请求即可制造记录：
   `fetch('https://no-such-host.invalid/x').catch(() => {})` → 主进程打出 `[Fireflux] 请求失败 … net::ERR_NAME_NOT_RESOLVED`，面板里也会出现这一条。

## 界面层的两个坑（Svelte 警告，已修）

- **非交互元素挂 `onclick`**：发布页的「改动文件名」原来是 `<code class="diff-link" onclick>`，Svelte 会报两条 a11y 警告
  （`a11y_click_events_have_key_events` / `a11y_no_noninteractive_element_interactions`），键盘用户也按不到。
  改成 `<button type="button">`，并把 `.diff-link` 复位成文本样式（`border/background/padding: 0`、`font: inherit`、`text-align: left`、`cursor: pointer`）——外观与行为不变，警告消失。
- **`$state(某个 prop)` 只捕获初值**：`Slider` 的数字框要「跟着 value 走、又允许用户中途输入」，所以必须有本地文本状态；
  直接写 `let text = $state(String(toDisplay(value)))` 会被报 `state_referenced_locally`。这里不适合用 `$derived`（文本还要被用户改写），
  正确写法是 `$state(untrack(() => String(toDisplay(value))))`：语义上明示「初值只取一次」，之后由 `$effect` 负责同步。

`pnpm build` 现在应当**零 Svelte 警告**；冒出新警告就是新引入的回归，别用 `svelte-ignore` 盖掉，按上面两条的思路改。

## 开发辅助

**性能 / 交互归因台**（改性能或看板娘代码前先跑；`scripts/bench-drag.mjs` 启动带探针的构建产物，
`src/main/services/drag-bench.ts` 是探针本体）：CPU 口径统一用系统级 PowerShell 采样全部 electron
进程的累计 CPU 秒数 —— Electron 自带 `getAppMetrics().percentCPUUsage` 在本机偏低约一个数量级，不可用。
探针只动被测量元素本身，不影响界面其它部分；例外是拖拽阶段会真实按下分隔条，逐页冒烟与互动测试会真实点击页面/看板娘（冒烟还会写整窗截图）。三种模式都不会去点「调整看板娘」开关，免得合成拖拽被当成调整操作写脏用户的大小/位置设置。

```bash
pnpm build                                       # 归因台跑的是构建产物（out/），改完代码先构建
node scripts/bench-drag.mjs                      # CPU 归因：静置 / 光标跟随 / 拖两条分隔条 + 几何校验
FF_INTERACT_TEST=1 node scripts/bench-drag.mjs    # 看板娘互动：唤醒、冻结、视线收敛曲线、跟随 CPU、命中
FF_SMOKE=1 node scripts/bench-drag.mjs            # 逐页冒烟，收集页面运行时报错
```

可选环境变量：`FF_BENCH_MS`（每阶段毫秒数，默认 2500）、`FF_L2D_RES`（临时改看板娘渲染分辨率再测，需 dev 同源）、
`FF_SHOT=<路径>`（存截图：冒烟＝整窗与编辑器，互动＝看板娘区域）。
结果以 `[bench]` / `[itx]` / `[smoke]` 前缀打印，CPU 归因模式的最后一行 `[bench-raw]` 是 JSON。

```bash
node scripts/hwgpu-test.mjs    # 硬件加速开关三态与崩溃自愈验证（会改 data/settings.json，跑完自动复位）
```

需要看 Chromium 的 GPU 能力时，手动带 `FF_GPU_INFO=1` 启动（`FF_GPU_INFO=1 pnpm start`），
主进程会打印 `[gpu-status]` / `[gpu-info]`。

这些脚本都会启动真实应用窗口；写死的应用行为（暂停、帧率、静止肖像）会直接影响读数，
所以它们只用于开发排查，不参与打包。
